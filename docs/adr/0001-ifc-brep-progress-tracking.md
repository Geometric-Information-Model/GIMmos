# IFC BREP load progress tracking

The IFC BREP read path (`GIMocctReadElements.LoadIfcDocWithProgress`) had no progress signal for most of its duration: `IFCReaderCLR.LoadDoc` (native IFC parsing via IfcOpenShell, `BuildShapeMap`, XCAF hierarchy assembly) and `GIMocctRead.ReadShapeTree` + `GetOcctCountRecursive` (the C# tree walk that first learns `shapeCount`) all used to run before `GimProgressStatus.Create` could even be called, since the entity totals it needs weren't known until after those phases finished — the bar looked frozen for the majority of a large IFC load. The fix is to call `Create` up front, before any of that runs, registering three buckets with **placeholder totals and fixed share weights** that never change; only the totals are corrected mid-flight via `AddTask`/`EntityCompletedCallback` as the real sizes become known.

**Status:** accepted

## The three buckets

- `PROGRESS_IFC_BOOTSTRAP` (weight 150, ~13.6%) — a synthetic ticker (`RunBootstrapProgress`), ticking once every 250ms up to a nominal total of 4800 (just under 20 minutes of headroom; the loop stops one tick short of the total so the bucket never looks complete on its own). It is the only signal during real stretches that have no native hook: the raw `IfcParse::IfcFile` parse, and the silent `BuildHierarchy`/XCAF assembly inside native `LoadDoc`. It also keeps ticking **in parallel** with `PROGRESS_IFC_LOAD`'s real callbacks for the rest of `LoadDoc` and during the C# shape-tree walk + count — both buckets contribute to `PercentageDone` at once during that window. It is cancelled (`ifcTailCts.Cancel()` in `ReadXcafDocumentToGimData`) only once `PROGRESS_ELEMENTS` is about to start, so it never competes with **element** ticks specifically, but it does overlap with load ticks for most of its life.
- `PROGRESS_IFC_LOAD` (weight 450, ~40.9%) — real, per-product progress from native `BuildShapeMap`, registered with a placeholder total of 1 and corrected via `AddTask(PROGRESS_IFC_LOAD, total)` on the first callback once the real product count is known. If the final `(processed, total)` callback never fires with `processed == total` (e.g. because filtered entities like `IfcSpace`/`IfcOpeningElement` are counted in `total` but never emit a callback), `LoadIfcDocWithProgress`'s `finally` block calls `ReadStatus.ForceCompleteTask(PROGRESS_IFC_LOAD)` as a safety net so the bucket doesn't stall below its share. If `LoadDoc` throws before the first callback ever arrives (`loadBucketStarted` still `false`), the bucket was never corrected — the caller cancels the bootstrap ticker instead and the read falls back (see below).
- `PROGRESS_ELEMENTS` (weight 500, ~45.5%) — the existing per-shape bucket (also used by the STEP/IGES and mesh-fallback paths), corrected via `AddTask(PROGRESS_ELEMENTS, shapeCount)` once the tree walk finishes.

## Why weights are fixed at `Create` time instead of derived from corrected totals

`GimProgressStatus.PercentageDone` is `sum(weight * completed/total) / sum(weight)`. If a bucket's weight were allowed to equal its (initially unknown) total, correcting that total mid-flight would also change the bucket's share of the bar retroactively, capable of moving the visible percentage backwards. Passing an explicit `weights` map to `Create` decouples "how much of the bar this bucket owns" from "how many units this bucket has to complete": correcting a placeholder total via `AddTask` (which also resets that bucket's completed count to 0) only rescales that bucket's own internal fraction — which starts at `0/1 = 0%` and stays `0` until real ticks arrive — never the weight sum in the denominator. Combined with the `maxPercentageReported` high-water mark in `PercentageDone` (a simple non-decreasing latch — never report a value lower than the highest already shown), the bar is monotone by construction even though two of its three bucket totals are unknown at start. `TestPlatform/GimProgressStatusTests.cs` encodes this monotone fixed-weight protocol, including the expected percentage milestones.

## Why the bootstrap phase is synthetic rather than removed

Some of the silent stretches genuinely have no native hook to attach to:

- `IfcParse::IfcFile`'s raw file parse (before `BuildShapeMap` even starts) is a third-party (IfcOpenShell) code path with no progress callback exposed.
- `BuildShapeMap`'s own callback is throttled to bound interop overhead: `reportEvery = max(2, totalProducts / 200)` in `IFCReader::BuildShapeMap` caps large files at roughly 200 managed/native crossings per load, while small files (fewer than ~400 products) are clamped to a callback every 2 products instead. On large, slow files the interval between two real callbacks can still span minutes, which would otherwise look like a stall.

A synthetic, timer-based ticker is the only way to give the user a liveness signal during these windows. It is intentionally capped (its own total is never fully reached — `RunBootstrapProgress` stops one tick short) so it can never look "done" on its own, and its small fixed weight (13.6%) bounds how much of the bar it can ever occupy, however long the silent stretches run.

## Failure and fallback behavior

If `IFCReaderCLR.LoadDoc` throws (native BREP parsing failed), the caller falls back to the IfcConvert/Assimp mesh path, which resets and re-`Create`s `GimProgressStatus` for a different plan. `RunBootstrapProgress`'s ticker keeps running on a background `Task` independent of that failure; its next tick calls `EntityCompletedCallback(PROGRESS_IFC_BOOTSTRAP)` against a bucket that no longer exists post-`Reset()`, which throws `KeyNotFoundException` — caught explicitly so the ticker terminates itself cleanly instead of crashing a thread-pool thread.

## Native-to-managed progress bridge

Real per-product progress crosses three layers:

1. **Native (`GIMocctWrapper/GIMocctCLI/IFCReader.h`/`.cpp`)** — `IfcLoadProgressCallback = std::function<void(size_t current, size_t total)>`, an optional parameter threaded through `IFCReader::LoadDoc` → `BuildShapeMap`. Invoked once with `(0, total)` before the loop, throttled during it (see above), and once more at the end with the true processed count (which can be less than `total`, since `total` counts all `IfcProduct` instances while `processed` only counts ones the geometry iterator actually emitted — filtered entities like `IfcSpace`/`IfcOpeningElement` never fire a callback).
2. **C++/CLI (`IFCReaderWrapper.h`/`.cpp`)** — `public delegate void IfcLoadProgressDelegate(int current, int total)` and an `IFCReaderCLR::LoadDoc(String^, IfcLoadProgressDelegate^)` overload. The managed delegate is captured by a `gcroot<IfcLoadProgressDelegate^>` inside a free (non-member) function `MakeProgressCallback`, which returns the native `std::function` invoked from native code. A lambda could not be defined directly inside the `ref class` member function — C++/CLI cannot host a native local class (a lambda) inside a managed method (compiler errors E2093/C3923) — so the lambda is hoisted out to a plain native function. The delegate invocation is wrapped in `try/catch (...)` so a misbehaving managed callback can never destabilize the native geometry loop.
3. **Managed (`GIMocctReadElements.LoadIfcDocWithProgress`)** — passes a C# lambda as `IfcLoadProgressDelegate`, which corrects `PROGRESS_IFC_LOAD`'s total on the first call and reports per-callback deltas via `EntityCompletedCallback(PROGRESS_IFC_LOAD, delta)`.

## Considered Options

- **Synthetic-only progress for the whole IFC load** — rejected: with no real signal at all, the bar's pace has no relationship to actual work; on slow files it either finishes far too early (looks done, then hangs) or is tuned conservatively and crawls uselessly on fast files. Purely cosmetic, not a liveness or ETA signal.
- **Real native callback only, no synthetic bootstrap** — rejected: the raw `IfcParse::IfcFile` parse has no hookable progress signal at all, and `BuildShapeMap`'s own throttled callback can go minutes between calls on large files; without a synthetic filler the bar would visibly stall during both.
- **Hybrid: synthetic bootstrap + real native callback, fixed-share weights, `AddTask` total correction** (chosen) — covers every phase with the best signal available for it, and the fixed-weight design keeps the bar monotone across two rounds of "we now know the real total" corrections.
- **Derive bucket weight from total at correction time (no explicit `weights` map)** — rejected: would let `AddTask` retroactively change a bucket's share of the bar, which can move `PercentageDone` backwards; the `maxPercentageReported` latch would then just mask an actual moving boundary rather than the boundary genuinely holding still.
